周五真人排练脚本：房间时间、设备接线与资料准备

用途
四名成员进行约五分钟的虚构安排讨论，展示一次真实操作闭环。主题是排练时间、投影接线与桌卡准备，不讨论研究统计，也不需要敏感真实资料。script.json 的台词用于引导讨论；在现场应以真人实际说出的内容和收到的聊天为准。

四个角色
1. 主持人：推动讨论，明确哪些安排必须确认，收到聊天后复述并落实或追问。
2. 数据负责人：负责演示资料和自己的设备，是部分参与者；前半段同时核对虚构资料清单。
3. 设计成员：负责封面、桌卡和现场引导，明确哪些意见可以晚答。
4. 开发成员：负责接线条件和演示流程，在被问及时补充设备信息。

分发角色卡
roles 中的 responsibilities 是公开职责，privateFacts 是各自扮演者掌握的背景。各人只看自己的背景即可。数据负责人需自行核对时间安排、电脑接口和已验证的设备情况；这些信息不是要预填到回复框的标准答案。
不要把整个 script.json 直接发给判定模型。未来台词、私有背景和 facilitatorNotes 均不应成为本轮模型输入。判定只使用已经发生的转写、目标成员公开职责和本人明确授权的设置。实际说出或手工发送的信息，之后才可成为会议上下文。

完整闭环
真人按台词自然说话
→ 实际音频被转写为文字
→ 将已经发生的转写交给 DeepSeek 判断是否需要目标成员关注或回应
→ 目标成员查看请求和来源，依据自己掌握的背景编辑回复
→ 本人复制文本，切到腾讯会议聊天，核对后手工粘贴并发送
→ 主持人看到真正收到的聊天，口头复述具体答复，说明安排如何改变或继续追问。

助手不自动发送，不代替本人承诺。复制到剪贴板不等于已经发送；聊天里出现文本也不等于其他人理解了，需要主持人的实际回应完成闭环。请按界面真实具备的功能操作；“编辑”“复制”等仍需现场验证。

当前依赖与演示边界
10月22日用户测试已记录本机麦克风转写进入DeepSeek并成功分析；远端组员声音和实际收发流程尚未验证。正式排练前，需确认腾讯会议里双方的声音都能进入当前转写入口。
优先做一个短链路检查：由真人说一条不在脚本中的无敏感内容的新句子，确认系统是否从本次音频产生相符文本，核对延迟与重复/漏字，再继续正式排练。
若实时转写尚不可用，可以由操作人员依据实际语音手工录入文字，明确标注“手工转写输入”；也可用 script.json 回放检查界面，明确标注“脚本回放”。两者都不能标为真实 ASR。
若无法自动取得说话人身份，可由操作人员确认或使用明确的发言标签，不宣称系统已经支持自动说话人识别。
连接 DeepSeek 后，要确认展示的是本次请求实际返回的结果。请求失败、超时或转写不全时保留失败状态；可以重试或请发言者重述，不拿预设判断与回复替换成“模型实时结果”。

五分钟节奏
00:00—01:15：说明目标，数据负责人继续资料核对。封面颜色与其有关但可晚答；提到其曾整理文件目录时明确不用答。
01:28—02:20：时间安排需要当场确认。主持人留出约40秒供查看、编辑、手工发送与回应。根据真实答复确认；没有答复就保留待定。
02:40—03:55：笼统的线材请求缺少接口与清单信息。允许先澄清。主持人收到澄清后让开发成员补充设备条件，再等数据负责人确认自己能承担的部分。
04:13—04:24：设计成员直接接下放桌卡的简单任务，用自己的清单即可；这里无需工具介入。
04:38—05:00：数据负责人恢复共同核对。主持人只总结已经确认的事项，未确认部分保留待办。

atSeconds 是参考开始时间，不是硬性播放器节拍。网络或操作变慢时宁可延长排练，不要为了五分钟预演成已收到答复。3:27 的设备条件可在真实澄清后提前补充；若此前无人澄清，就按台词主动补充，不把这次补充记成助手促成。

录屏拍摄提纲
A. 开场说明与界面
用十余秒说明四人角色、虚构排练任务，以及当次输入是实时转写、手工转写还是脚本回放。画面保留会议、助手和聊天的实际界面，隐藏无关窗口、账号及真实个人资料。录制前确认参与者同意。

B. 可晚答与无需答
拍到封面意见和文件目录提及的真实发言及模型实际输出。模型如何处理就如实保留，不要求每个节点都“判断正确”；未出现提醒也不要只凭画面推断系统已正确理解。

C. 当场确认的完整链路
从时间请求开始，连续拍到转写出现、模型结果、本人核对和编辑、复制、切换聊天、手工发送，以及主持人复述实际内容。画面应能分清草稿、已发送和已被回应；私有背景可以用角色卡口头交代，不必把完整角色卡传给模型或暴露到会议里。

D. 信息不足与澄清
拍到笼统设备请求、本人提出的真实澄清、开发成员补充条件，以及后续本人确认。若模型直接给出无依据结论，保留本人修改或拒绝的过程，不把错误段剪掉再称为完整链路。

E. 不需要工具的片段与结束
保留设计成员直接处理桌卡、部分参与者恢复共同核对的短片段。以当前已确认和待确认事项收尾。若演示视频剪去等待或跨多轮拼接，要明确标记，不能造成一次连续实时运行的印象。

排练后记录
只记录实际发生的输入方式、转写内容、模型输出、本人改动、是否真正发送、主持人如何理解，以及失败或等待在哪一步。参考时间不能作为实测延迟；没有准确记录就不报耗时。
一次顺利排练说明流程可以走通，不证明效率提高、漏答减少或研究假设成立。普通直接沟通已足够的片段也应保留。

演示或试用结束后的反馈
请参与者点击助手顶部“使用反馈”，选择实际体验到的阶段，指出一个具体时刻或问题。
可以描述有帮助的地方、不需要助手的地方，或希望怎样改；评分可以不填。
如参与者只观看演示，不要求其判断尚未体验的转写准确率、操作负担或实际响应速度。
在同一电脑上可连续填写多份反馈；参与编号可用于后续区分同一人的多条意见。
反馈保存在运行助手的电脑，重启不丢。异地试用需要导出反馈文件后交给项目组。
整理时按“具体反馈、设计启发、实际修改、验证结果”对应，保留未采纳意见及理由。

附录：本机录屏页（2026-10-22）
从助手入口另开“本机录屏”，或在本机服务地址后打开 /recorder.html。原来的四人、约五分钟剧本与角色卡继续使用。
1. 先安排腾讯会议与助手并排。需要同时拍到两个窗口及切换操作时，在浏览器共享框中选择整个屏幕；关闭无关窗口、通知与真实个人资料，取得参与者同意。
2. 勾选“尝试录入共享画面的声音”，并在浏览器共享框中允许系统音频（如果提供）；需要本人发言或旁白时再勾选麦克风。只录画面则两项均取消。使用耳机减少重复收音。
3. 先做约10秒检查，再停止并回放。页面显示“取得音轨”只说明浏览器返回了轨道，不能保证远端声音和本人发言清晰可听。共享窗口、标签页或整个屏幕支持的声音可能不同。
4. 短录制检查通过后再正式开始；开场明确本轮是实时语音、手工转写还是剧本回放。切回会议和助手开展排练，录屏标签页保持打开。录屏与助手会话独立，停止助手会话后仍可继续录下结束说明。
5. 完成后回录屏页点“停止录制”，等最后片段收取完，再点“保存 WebM”。浏览器下载完成后打开文件检查；保存按钮仅发起下载，不代表已核验磁盘文件。
6. 录像只暂存在录屏页内存，此页不上传视频；刷新或关闭会丢掉未下载内容。遇到中断时可保存浏览器已交出的片段，并检查是否完整。不要把权限/设备的模拟测试结果当成真实录制成功。

录屏与语音识别是两条不同的链路。此录屏页使用浏览器采集与 MediaRecorder，不需要 API Key，也不调用语音识别。助手现有浏览器 SpeechRecognition 路径不要求另填 ASR Key；但有些浏览器（如 Chrome）可能使用服务端识别并发送音频到识别服务，不能称为纯离线，服务可用性仍须实测。DeepSeek 的模型 Key 属于另外的分析步骤。
